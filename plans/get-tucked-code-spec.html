Get Tucked

Engineering spec · v0.1 · status: specced · iOS native · paid one-time, no recurring

Working name during development is Get Tucked. The App Store name will be Tuck if Apple rejects the working name (which is plausible given the pun). Design assets should accommodate both.

1. Problem

Bikepackers and ultra-distance racers spend months tuning setup. Bag placement, layering, cockpit choices, posture in the saddle. They make these decisions on feel because nothing in their price range quantifies the trade-offs. Wind tunnel time costs thousands of dollars. Aero sensors like Notio or Aerolab cost over USD $1,000 and target race riders. Below that floor, riders are flying blind.

2. Concept

An iOS app that measures rider frontal area from calibrated photos. The user photographs a position, the app extracts the silhouette, computes area in square centimetres, and saves the result. Comparing two positions surfaces the percentage difference and names the posture changes. Tap any bag in a photo to segment it and see what that piece of luggage costs.

Built for the audience that iterates setups across a season, not the audience chasing 5 watts in a tunnel.

3. What this is, and what it is not

This is a measurement tool. It is not a wind tunnel.

The app does not predict CdA. It does not run CFD. It does not model airflow. It measures frontal area from photos and reports posture angles from pose estimation. Differences are expressed as percentages relative to a user-chosen baseline.

The honest framing matters because the alternative is shipping fake numbers with three decimal places that nobody can validate. Coaches spot it instantly. Reviewers hammer it. Users lose trust.

Every number the app shows must be defensible. If the engineering team cannot explain how a number was computed in two sentences, the app does not display it. The "How this works" screen (see §11) is non-negotiable and ships in v1.

4. Audience

Primary: bikepackers and ultra-distance racers who iterate setups across months. Tour Divide, Race Across France, Atlas Mountain Race, GBduro, Silk Road Mountain Race types. Plus the larger weekend bikepacking audience that will not race but enjoys quantification.

Secondary: time trial and triathlon riders comparing tucks. Same tool, different example imagery. Not pursued in v1 but the product must not actively exclude them.

Not the audience: riders who need absolute CdA numbers for race strategy. They already own Notio, Aerolab, or a tunnel booking.

5. Tech stack

  • Language: Swift 5.9+
  • UI: SwiftUI primary, UIKit interop where needed (custom camera UI, segmentation overlay)
  • Minimum OS: iOS 17 (required for Vision foreground subject extraction, which the bag overlay depends on)
  • Frameworks:
    • ARKit for camera pose, gravity alignment, plane detection during capture
    • Vision for person segmentation, pose estimation, foreground subject lifting
    • AVFoundation for the capture session
    • PhotoKit for storing source photos in the user's library
    • SwiftData for app metadata (positions, bikes, events, metrics)
    • Core Image for compositing and overlay rendering
  • No backend. No third-party cloud services. No analytics in v1, or opt-in via Apple's standard mechanisms only.
  • Device support: any iPhone running iOS 17. LiDAR (Pro models) adds a confidence boost where available, but the non-Pro experience is canonical. Pro-only features are out of scope for v1.

6. Data model

Position

The core unit. Immutable once captured. Re-shooting creates a new Position rather than editing an existing one.

Position {
  id: UUID
  capturedAt: Date
  bikeId: UUID?         // nullable; "no bike assigned"
  eventIds: [UUID]      // zero or more events
  label: String         // user-given, e.g. "Hoods, fully loaded"
  packingList: String?  // free text, e.g. "Frame bag, fork bags x2..."

  // Capture
  photos: [PhotoRef]    // typically 2 (head-on + side-on), more allowed
  scaleReference: ScaleReference  // handlebar width in cm, source photo

  // Derived metrics (recomputed from photos when the analysis pipeline updates)
  metrics: PositionMetrics
}

PhotoRef {
  photoLibraryIdentifier: String  // PHAsset local identifier
  angle: CaptureAngle             // .headOn | .sideOn | .threeQuarter
  cameraPose: CameraPose          // from ARKit at capture time
  qualityFlags: [QualityFlag]
}

PositionMetrics {
  frontalAreaCm2: Double
  frontalAreaUncertainty: Double  // ±, from user's noise floor
  torsoAngleDeg: Double
  hipAngleDeg: Double
  headDropCm: Double
  shoulderRollDeg: Double
  armWidthCm: Double
  bagSegments: [BagSegment]       // user-tapped bag masks with areas
  computedAt: Date
  pipelineVersion: String         // so re-analysis is possible later
}

BagSegment {
  id: UUID
  label: String?         // user-assigned, e.g. "seatpack"
  maskData: Data         // compact PNG mask
  areaCm2: Double
  colourHex: String      // for overlay rendering
}

Bike

  id: UUID

  wheelbaseCm: Double?          // optional secondary reference

Event

Events are tags with a date, not folders. A Position can belong to multiple events. This is what unlocks timeline views ("setup evolution leading into Tour Divide").

  notes: String?
}

UserSettings

  noiseFloorLastCalibrated: Date?

}

7. Capture pipeline

Capture is the make-or-break system. Bad input gives bad output, and bad output kills trust. The pipeline must refuse bad captures with specific feedback, not silently accept garbage.

Pose enforcement (ARKit)

  • Side-on capture: phone gravity-aligned, level within ±2°. Camera height between rider's hip and chest. Phone perpendicular to the bike's wheel plane within ±5°.
  • Head-on capture: same level requirement. Phone perpendicular to the bike's forward axis within ±5°.
  • The capture button is disabled until tolerances are met. The UI shows the user why it is disabled in real time.

Subject detection (Vision)

  • Single person required. Reject if zero or multiple people detected.
  • Person must occupy a reasonable portion of the frame (heuristic: bounding box height > 50% of frame height).
  • Reject if person bounding box clips the frame edge.

Background quality

  • Run segmentation in real time during framing. Compute a confidence score on the foreground/background split.
  • If confidence is below threshold, surface specific guidance: "background too cluttered behind rider's left shoulder", "low contrast on left side", "strong backlight detected".
  • Refuse the capture if confidence falls below a hard floor.

Scale reference

  • User has entered handlebar width for the selected bike.
  • Vision detects handlebar endpoints in the photo. If detection fails, fall back to user-tap calibration ("tap each end of your handlebars").
  • Known length in cm, known length in pixels, plus ARKit camera intrinsics, gives absolute scale.

Multi-capture

  • Each "position" capture takes 3 photos in quick succession (think Touch ID enrolment).
  • Pipeline computes metrics from each photo independently, reports the median, and uses the spread to populate per-position uncertainty.
  • If spread is too high (rider moved between shots), prompt to retry.

8. Analysis pipeline

Frontal area

This is the hero metric. From a head-on photo with absolute scale, the calculation is:

  1. Vision returns a person segmentation mask.
  2. Count foreground pixels.
  3. Convert to real-world area using camera intrinsics and the established scale.

This is a planar projection. It assumes the rider is roughly in a single plane perpendicular to the camera. The assumption is good enough for relative comparisons. It is not good enough to call the output CdA.

Engineering callout: the area calculation is not "Vision returns frontal area in cm²". The framework gives you a mask. Converting that to a real area requires camera intrinsics handling, scale propagation, and uncertainty estimation. Budget real engineering time for this. It is the most important math in the app.

Posture metrics

From Vision's pose estimation (returns 3D joint positions for a single person):

  • Torso angle: angle between shoulder-hip line and the gravity vector
  • Hip angle: angle at the hip joint (torso to thigh)
  • Head drop: vertical distance from shoulder midpoint to top of head, projected to the saddle plane
  • Shoulder roll: rotation of shoulder line relative to bar line
  • Arm width: horizontal distance between elbow joints

These are reported individually as diagnostics. They do not roll into a composite score. Frontal area is the headline; posture metrics tell the story behind it.

Bag segmentation

Bag overlay uses Vision's foreground subject lifting (iOS 17+, the same API powering "lift subject from background" in Photos).

  • User taps a bag in the photo.
  • Vision returns a mask for the tapped subject.
  • App computes the area of that mask.
  • User assigns a label.
  • Each bag gets a colour for overlay rendering.

This is iterative. Each tap adds one bag. Each bag is independently editable, deletable, and re-segmentable.

Noise floor self-test

During onboarding, after the first successful capture, prompt the user to capture the same position again. Compute the percent difference in frontal area between captures. Average over a few captures to establish a personal noise floor.

  • Store as UserSettings.noiseFloorPct.
  • Display alongside every comparison: "Difference: 8.2%. Your noise floor: ±2.1%."
  • If a comparison delta is below the noise floor, the UI labels it "indistinguishable", not "0.3% different".
  • Suggest recalibration after 90 days or after the user changes phones.

9. Comparison logic

Baseline

A baseline is a Position the user marks as their reference. Default suggestion: the bike without bags. Users can change the baseline at any time, or pick any two positions for an ad-hoc comparison.

Detailed view (2-up)

  • Two positions side by side, photos with silhouette overlays.
  • Headline: percent delta in frontal area between A and B.
  • Below: diff list naming posture changes ("head 3 cm lower, shoulders rolled 2°, frame bag added").
  • Silhouette overlay toggle: A only, B only, both overlaid, neither.
  • Bag visibility toggle per bag.

Leaderboard

All positions on a single bike (or in a single event), ranked by frontal area. Smallest first. Each row shows percent delta from the user's baseline.

Cross-bike comparison

Allowed, but the UI surfaces a warning: "These positions are on different bikes. Differences may reflect the bikes, not the rider." Comparison still works; the warning makes the limitation visible.

Below-noise-floor handling

If |delta| < noiseFloorPct, the comparison shows "indistinguishable" in place of the percent. Hovering or tapping reveals the actual computed delta and the noise floor explanation. This is the single most important honesty feature in the app.

10. Storage and privacy

What's stored where

  • Source photos: user's Photo Library, via PhotoKit. The app does not maintain a separate copy.
  • Position metadata, bikes, events, derived metrics: SwiftData store, app-private.
  • Masks (segmentation, bags): app-private, derived data, regenerable from source photos.

Privacy posture

  • No cloud sync in v1. Everything is on-device.
  • No analytics in v1, or opt-in via Apple's standard mechanism.
  • At first capture, the app shows a consent reminder: "Photos stay on your device. Only capture people who have agreed to be measured." The user acknowledges once. Stored as consentToCaptureOthers.
  • Standard Apple privacy nutrition labels apply. Honest answers only.

Future-proofing

Derived metrics are stored with a pipelineVersion. If a future version improves the analysis pipeline, old positions can be re-analysed from their stored photos. The app offers but does not force this.

11. Methodology transparency ("How this works")

Reachable from any screen that shows a number. Contents:

  • Plain-language description of how frontal area is computed
  • List of inputs (photo, handlebar width, ARKit camera pose) and outputs (cm², percent delta)
  • List of what the app does not do (CFD, yaw, drag prediction, wind modelling)
  • Limitations (planar projection assumption, scale-reference dependence on accurate handlebar width, segmentation accuracy under poor lighting)
  • Citations to underlying research: Defraeye et al, Crouch et al, García-López et al, and a couple of accessible overview articles
  • Honest statement of measurement uncertainty and what the user's noise floor means

This screen is a differentiator. No comparable app in the category does this well. It is also the screen that justifies the price.

12. Failure states

Capture failures (refuse and explain)

ConditionUser-facing message
No person detected"No rider found in frame. Step back so your full body is visible."
Multiple people detected"Looks like more than one person is in frame. Ask helpers to step out of view."
Person clipped at edge"Your [head/feet/elbows] are cut off. Step back or recompose."
Phone not level"Phone is tilted. Hold it level (use the on-screen guide)."
Phone not perpendicular"You're capturing from an angle. Move to face the bike directly."
Low segmentation confidence"Background is making you hard to separate. Try a plain wall behind you."
Strong backlight"Light is behind you, washing out your edges. Move so the light is in front."
Handlebar endpoints not detected"Couldn't find your handlebars automatically. Tap each end to calibrate."
Multi-capture spread too high"You moved between shots. Hold still and try again."

System failures

  • Camera permission denied: explain why it's needed, deep-link to Settings.
  • Photo Library permission denied: same.
  • Motion permission denied (ARKit needs it): same.
  • Storage full: surface before capture, not after.
  • Backgrounded mid-capture: discard the in-progress session, return to the previous screen without prejudice.
  • ARKit unsupported (unlikely on iOS 17 devices, but possible): graceful fallback to non-AR capture with a quality warning.

Logical edge cases

  • Entered handlebar width does not match what's visible in frame (sanity check fires): "Your bars look wider than 42 cm in this photo. Double-check the bike."
  • Bag tap selects nothing useful: "Couldn't isolate a subject there. Try tapping the centre of the bag."
  • Delta below noise floor: "Indistinguishable from your baseline within measurement precision."
  • Cross-bike comparison: warning banner, comparison still computed.

13. Engineering callouts

Things that look easy in the spec but are not:

  1. Frontal area math. Camera intrinsics, scale propagation, uncertainty. Not a one-liner. Budget time.
  2. Real-time pose enforcement during capture. ARKit + AVFoundation interop is fiddly. Expect a week of tuning the "is this shot acceptable" logic.
  3. Multi-capture aggregation. The right way to combine N captures of the same position (median? trimmed mean? weighted by ARKit confidence?) is empirical. Plan to iterate.
  4. Bag segmentation UX. The Vision foreground subject API works well on simple cases. Real bikes with bags overlapping bags will need careful UX (re-tap, edit mask, etc.).
  5. Noise floor self-test. The pedagogy is harder than the math. Users need to understand what they're being asked to do and why.
  6. App Store review of the name. If "Get Tucked" is rejected, have "Tuck" pre-prepared. Do not let this become a launch blocker.

14. Build phases

Vertical slices. Each phase ships a coherent working product, even if a small one.

Phase 1: skeleton

  • Xcode project, SwiftUI app shell
  • Bike model, single-bike onboarding, no events yet
  • Single capture (head-on only), no AR enforcement, no segmentation refusal
  • Vision person segmentation → frontal area in cm²
  • Save a Position, list of Positions, view one
  • No comparison yet. No bags. No posture metrics.

Stop here, review. Confirm the area numbers look plausible against a known reference.

Phase 2: pose, comparison, AR enforcement

  • Posture metrics from Vision pose estimation
  • Side-on capture added; both angles required for a complete position
  • ARKit pose enforcement during capture (level, perpendicular)
  • 2-up comparison view with overlaid silhouettes
  • Leaderboard view for a single bike

Phase 3: bags

  • Tap-to-segment bag flow via Vision foreground subject lifting
  • Bag list per Position, per-bag area, per-bag colour
  • Bag visibility toggles in the comparison view

Phase 4: events, timeline, self-test

  • Events as tags with dates
  • Position can belong to multiple events
  • Timeline view for an event ("setup evolution into Tour Divide")
  • Noise floor self-test, surfaced in onboarding and recallable from settings
  • Below-noise-floor handling everywhere

Phase 5: polish

  • "How this works" methodology screen, fully written
  • Accessibility pass: VoiceOver labels for silhouettes and metrics, Dynamic Type support
  • Failure copy review across all states
  • The reveal-moment motion design pass
  • App Store submission prep, screenshots, marketing site
